## 你的模型没问题，问题在别的地方

有人做了一个实验：同一个模型，什么都没改，只是换了工具调用接口的格式，编码基准分数从 6.7% 直接跳到 68.3%。

模型没有变聪明。变的，是模型外围那套系统。

这个实验让很多团队开始反思一件事：为什么我们用了最贵的模型，Agent 跑起来还是各种拉胯——重复犯错、做到一半放弃、越跑越蠢？

答案越来越清晰：瓶颈从来不在模型。在 **Harness**。

---

## 一、Harness 是什么

一句话定义：**Agent = Model + Harness**。

模型负责推理，剩下的全部是工程。工具调用、上下文管理、权限控制、反馈回路、文件系统、沙箱环境——这些统称 Harness。

你不是模型，那你就是 Harness。

理解 Harness 最好的方式，是先搞清楚它和 Prompt Engineering、Context Engineering 的关系。三者不是并列的，是嵌套的：

| 层级 | 解决什么 | 关注点 |
|------|---------|--------|
| Prompt Engineering | 表达——怎么写好指令 | 让模型听懂你的意图 |
| Context Engineering | 信息——给 Agent 看什么 | 确保模型拿到正确信息 |
| Harness Engineering | 执行——整个系统怎么防崩 | 长链路任务中持续正确、故障恢复 |

Phil Schmid 有个类比说得最到位：**模型是 CPU，Harness 是操作系统。** CPU 再强，OS 拉胯也白搭。你买了最新的芯片，装了个崩溃不断的系统，体验还不如老芯片配稳定的 OS。

简单任务里，把 Prompt 写好就够了。但当任务变长、变复杂、容错率变低，Harness 才是决定成败的东西。LangChain、Anthropic、OpenAI 的工程团队，重心都已经放在 Harness 上。

## 二、上下文越多，Agent 越蠢

这是 Harness Engineering 里最反直觉、也最重要的一条经验。

Dex Horthy 做了量化实验：以 168K token 的上下文窗口为例，**用到大约 40% 的时候，Agent 的输出质量就开始明显下降。**

| 区间 | 表现 |
|------|------|
| 0 ~ 40%（Smart Zone） | 推理聚焦、工具调用准确、代码质量高 |
| 超过 40%（Dumb Zone） | 幻觉增多、兜圈子、格式错误、低质量输出 |

Anthropic 在自己的实践中也碰到了类似现象，他们叫"上下文焦虑"：模型在上下文快填满时会变得犹豫，倾向于提前收工——哪怕任务还没做完。

他们最终的做法不是压缩，而是直接**清空上下文窗口**，启动一个全新的 Agent，通过结构化交接文档把关键状态传递过去。类似重启进程解决内存泄漏。

**你的目标不是给 Agent 塞更多信息，而是让它在任何时候都运行在干净、相关的上下文里。**

工程实践的第一条经验法则：**监控上下文利用率，设置 40% 告警阈值。** 等到 Agent 已经变蠢了再处理，就晚了。

## 三、四件必做的事

一线团队各自独立实践，最终 converge 到了四个共同模式。这不是巧合，是工程规律。

### 1. 上下文分层：AGENTS.md 当目录用，不当字典用

很多团队踩过同一个坑：把所有规则塞进一个巨大的 AGENTS.md，结果上下文窗口被撑爆，Agent 反而更蠢。

OpenAI 后来的做法是：**AGENTS.md 只当目录（约 100 行），详细规则放在子文档里，按需加载**。一个后台 Agent 定期扫描过期文档、提交清理 PR——由 Agent 为 Agent 维护文档。

核心原则：**渐进式披露**。Agent 需要什么信息，再给什么信息。不要一开始就全部倾倒。

### 2. Agent 专业化：专才永远比通才靠谱

把所有权限都给一个通用 Agent，不如让多个专业 Agent 各司其职。

原因不只是组织层面的——**专业化本身就是上下文管理策略**。每个专家携带的无关信息更少，天然运行在 Smart Zone 内。

Anthropic 在构建 C 编译器项目时，把 Agent 分为四类角色：编译器核心、去重、性能优化、文档。其中专门有一个"去重 Agent"——因为 LLM 生成的代码经常重新实现已有功能，这个问题严重到需要一个专职 Agent 来处理。

另一个团队 Vasilopoulos 部署了 19 个领域特定的 Agent，每个都只聚焦自己的领域。

### 3. 持久化记忆：状态存文件系统，不存上下文窗口

每次新 Agent 会话从零开始。不做记忆持久化，等于让一个失忆的工程师每天重新上岗。

Anthropic 的两阶段方案值得参考：**初始化 Agent** 负责建立 init.sh、进度文件和初始 git 提交；**后续编码 Agent** 每次做出增量进展后留下结构化更新。

他们发现了一个细节：用 JSON 追踪功能状态比 Markdown 更有效——因为 Agent 不太会不小心破坏结构化数据，而 Markdown 经常被改乱。

Hashimoto 的 AGENTS.md 有一条朴素但有效的规律：**文件里的每一行，都对应一个过去 Agent 的真实失败案例**。失败了就写进去，永久预防。他每天下班前启动 Agent，让它夜间工作，第二天早上拿到"暖启动"的成果开始上班。

### 4. 先规划，再执行

Boris Tane 说得最直接："**永远不要让 Agent 在你审查和批准计划之前写一行代码。**"

把思考和执行分开：理解 → 规划 → 执行 → 验证。

Anthropic 把这个做到了极致：初始化 Agent 先生成超过 200 个功能的结构化列表，全部标为 failing；后续 Agent 每次只处理一个功能，完成后提交 git 和进度更新。拆得足够细，才能做到真正可控。

## 四、从哪里开始

不要试图一开始就搭齐所有层。**先把 P0 做完，效果就会很明显。**

**P0：立即可以做**

| 行动 | 为什么 |
|------|--------|
| 创建 AGENTS.md 并持续维护 | Agent 每次启动自动加载，犯错就更新，形成反馈循环 |
| 构建自定义 Linter + 修复指令 | 错误消息直接告诉 Agent 怎么改，纠错的同时在"教"它 |
| 把团队知识放进代码仓库 | 写在 Slack 和 Wiki 里的知识对 Agent 等于不存在 |

**P1：P0 做完后考虑**

上下文分层管理、建立 JSON 格式的进度追踪文件、给 Agent 端到端验证能力（如 Playwright 自动化）、监控上下文利用率不超过 40%。

**P2：有余力再做**

Agent 专业化分工、定期垃圾回收（清理 AI 生成的冗余代码）、接入可观测性工具。

对照下面的成熟度阶段，判断自己在哪里、下一步该做什么：

| 阶段 | 特征 |
|------|------|
| Level 0 | 直接给 Agent prompt，无任何结构化约束 |
| Level 1 | AGENTS.md + 基础 Linter + 手动测试 |
| Level 2 | CI/CD 集成 + 自动化测试 + 进度追踪 |
| Level 3 | 多 Agent 分工 + 分层上下文 + 持久化记忆 |
| Level 4 | 无人值守并行化 + 自动化熵管理 + 自修复 |

## 结语：工程师的角色在变

OpenAI 的一个团队，三名工程师五个月构建了百万行代码的产品，手写代码 0 行。Anthropic 两周用 16 个并行 Agent 造出了能编译 Linux 内核的 C 编译器。

这些不是未来，是正在发生的事。

工程师的角色，正在从"写代码"转向"**设计让 AI 能正常干活的环境**"。

Harness Engineering 的核心不是某个具体工具，而是一种思维方式的转变：**你的工作不是提示词调优，而是系统设计——设计约束、设计反馈、设计记忆、设计失败恢复。**

模型会越来越强。但在同样的模型能力下，谁的 Harness 更扎实，谁的 Agent 就更可用。这是 2026 年 AI 应用真正的差异化战场。
