如果你用大模型写过代码，大概经历过这样的过程：

你把需求描述得很清楚，模型也给出了看起来很完整的答案。可是把代码真正运行起来以后，报错了；你把报错信息复制回去，它又修了一个地方，却引入了另一个问题。如此来回几次，有时候终于能跑通，有时候则会陷入“再试一次”的循环。

很多 Agent Demo 展示的是模型第一次输出得有多漂亮，但真正决定 Agent 能不能完成复杂任务的，往往不是第一次输出，而是**它能不能根据环境反馈持续修正自己的行为**。

这就是我理解的 Loop Engineering。

这里的 Loop Engineering 并不是一个已经有严格统一定义的学术术语。我更愿意把它看成一种 Agent 工程方法：**围绕反馈、评估、修正和退出条件，设计一个能够稳定推进任务的执行循环。**

## 一、Agent 的核心不是一次回答，而是一个循环

普通的聊天交互通常是这样的：

```text
用户输入 -> 模型回答
```

但一个真正需要执行任务的 Agent，更接近这样：

```text
读取状态 -> 选择行动 -> 执行动作 -> 观察结果 -> 评估进展 -> 修正计划
                 ^                                      |
                 |______________________________________|
```

模型在每一轮里并不是单纯地“继续生成文字”，而是在回答几个问题：

- 现在任务进行到哪一步了？
- 刚才的动作是否真的产生了预期效果？
- 当前遇到的是偶然错误，还是方案本身不成立？
- 下一步应该继续尝试、回滚、换一条路径，还是停止？

如果没有这个循环，Agent 其实只是在生成一份计划。计划写得再详细，也不能保证计划已经被执行，更不能保证执行结果符合目标。

## 二、Loop Engineering 和几个相近概念的区别

前面写 Harness Engineering 的时候，我把 Agent 描述成：

> Agent = Model + Harness

这个公式解决的是 Agent 的工程底座问题。Loop Engineering 关注的则是：**这些底座如何被组织成一个可以不断推进任务的闭环。**

可以简单地这样理解：

| 概念 | 主要解决的问题 | 关注点 |
|------|----------------|--------|
| Prompt Engineering | 怎么告诉模型应该做什么 | 指令表达 |
| Context Engineering | 这一轮让模型看到什么 | 信息选择 |
| Harness Engineering | Agent 运行需要哪些基础设施 | 工具、权限、记忆、调度 |
| Loop Engineering | Agent 如何根据结果继续推进 | 反馈、评估、修正、退出 |

这几个概念并不是互相替代的关系。

一个 Agent 需要工具调用能力，这是 Harness 的问题；它需要知道上一步命令的输出，这是 Context 的问题；它需要在测试失败后修改代码并重新测试，这是 Loop 的问题。

如果把 Agent 比作一个人在工厂里完成订单，那么 Prompt 像是订单说明，Context 像是工作台上当前摆放的材料，Harness 像是工厂的设备和安全制度，而 Loop 则是“做一件、检查一件、发现不对就返工”的生产流程。

## 三、一个可靠的执行循环应该包含什么

一个最小可用的 Agent Loop，至少应该包含下面五个阶段。

### 1. 计划：把目标拆成可以验证的子目标

“实现一个用户系统”不是一个好的循环目标，因为它太大，也没有明确的完成标准。

“新增用户注册接口，并通过已有的注册测试”就更适合作为一个子目标。它至少包含了三个信息：要做什么、影响哪里、怎样判断完成。

计划的意义不是让模型一次性写出一份完美方案，而是让每一轮行动都有一个相对明确的方向。计划应该允许被后续反馈修改，否则它就会变成另一种形式的僵化 Prompt。

### 2. 行动：每一轮只做有边界的事情

Agent 可以调用工具、修改文件、执行命令、访问数据库，也可以向用户请求信息。但一次循环中的动作最好有清晰的边界。

比如，不要让 Agent 在没有检查的情况下同时修改十几个模块，然后最后才运行测试。更好的方式是：先定位相关文件，完成一个局部修改，立即运行对应检查，再决定下一步。

动作越大，失败以后越难判断是哪一步出了问题；动作越小，反馈就越有解释力。

当然，动作也不能小到让 Agent 只会机械地执行几十个没有意义的步骤。工程上的关键是找到一个合适的粒度：**一次动作应该足够产生进展，也足够容易被验证。**

### 3. 观察：把环境结果带回循环

执行动作以后，Agent 必须看到真实结果。

对于编程任务，观察结果可能是：

- 编译器输出；
- 单元测试结果；
- 日志和异常堆栈；
- Git diff；
- 页面截图或浏览器交互结果。

对于数据分析任务，观察结果可能是查询结果、数据分布、评估指标；对于自动化任务，则可能是接口响应、文件状态或业务系统中的实际变化。

观察不是简单地把所有日志都塞回上下文。日志应该经过裁剪、结构化和排序，让模型看到真正有助于决策的信息。例如测试失败时，错误类型、失败用例、相关堆栈和最近一次变更通常比完整的构建日志更有用。

### 4. 评估：判断是进展、失败，还是没有变化

Agent 不能只根据“命令执行成功”判断任务成功。

一个命令返回 0，可能只代表程序没有崩溃，并不代表功能正确。一个测试通过，也可能只是测试覆盖不足。评估层需要回答的是：**当前状态距离目标还有多远？**

评估可以分成几层：

```text
语法检查       代码能不能被解析
单元测试       局部逻辑是否正确
集成测试       模块之间能不能协作
行为验证       用户看到的结果是否符合需求
业务指标       线上效果是否达到目标
```

越靠近用户目标的评估越有价值，但成本通常也越高。因此可以先用便宜的检查快速过滤明显错误，再用更接近真实目标的检查做最终确认。

### 5. 修正或退出：下一步不一定是“再试一次”

发现失败以后，最容易写出的逻辑是：

```text
失败 -> 把错误信息交给模型 -> 再执行一次
```

但“再执行一次”并不是策略。下一步可能有很多种选择：

- 修正当前实现；
- 回滚最近一次变更；
- 换一个工具或方案；
- 缩小任务范围；
- 请求用户补充信息；
- 直接停止并报告阻塞原因。

可靠的循环应该让模型在这些选项之间做选择，而不是把所有失败都归类为“继续重试”。

## 四、反馈是 Loop Engineering 的燃料

没有反馈的循环，只是重复执行；质量很差的反馈，则会把 Agent 引向错误方向。

我认为好的反馈至少需要满足三个条件。

### 反馈必须和目标相关

如果目标是“接口返回正确的用户信息”，那么 HTTP 状态码、响应字段和权限行为比一大段服务器日志更重要。

如果目标是“修复一个排序问题”，那么固定样例上的排序结果、边界输入和回归测试比模型自己说“看起来已经修好了”更可靠。

### 反馈必须尽量客观

“这个实现好像不太对”对模型的帮助很有限；“当输入为空数组时，函数返回 1，但预期为 0”就可以直接指导下一步修改。

这也是为什么自动化测试、类型检查、Schema 校验和静态分析在 Agent 系统中非常重要。它们不是单纯的质量保障工具，也是给模型提供判断依据的传感器。

### 反馈必须能区分不同类型的失败

并不是所有错误都应该交给同一个修复策略。可以把失败大致分为：

| 失败类型 | 典型原因 | 更合适的处理方式 |
|----------|----------|------------------|
| 输入错误 | 缺少参数、需求不完整 | 请求补充信息 |
| 环境错误 | 网络、权限、依赖不可用 | 检查环境或暂停 |
| 实现错误 | 代码逻辑不正确 | 修改并重新验证 |
| 方案错误 | 当前路线无法满足约束 | 回退并重新规划 |
| 目标冲突 | 不同要求互相矛盾 | 暂停并交给用户决策 |

如果网络断了，盲目让模型修改代码没有意义；如果单元测试持续失败，继续在同一个位置打补丁也未必是正确选择。错误分类的目的，就是让循环具备“换挡”能力。

## 五、不要把重试次数当成可靠性

在很多 Agent Demo 里，循环逻辑可能只是：

```python
for i in range(10):
    result = agent.run(task)
    if result.success:
        break
```

这段代码看起来很有韧性，但它并没有定义什么是 success，也没有记录每轮发生了什么，更没有判断循环是否真的在接近目标。

一个更完整的循环，至少应该保存状态和进展：

```python
state = load_state()

while not state.done:
    if state.budget_exhausted():
        return stop("达到时间或成本上限")

    action = model.choose_action(
        goal=state.goal,
        observations=state.relevant_observations(),
        history=state.compact_history(),
    )

    observation = execute(action)
    state.record(action, observation)

    evaluation = evaluator.check(state)
    state.record_evaluation(evaluation)

    if evaluation.completed:
        return finish(state)
    if evaluation.blocked:
        return stop(evaluation.reason)
    if state.no_progress_for(3):
        state.request_replan()
```

这里有几个容易被忽略的点。

第一，循环的结束条件应该由目标状态决定，而不是由模型说“完成了”决定。第二，时间、Token、工具调用次数和修改范围都应该是预算的一部分。第三，需要识别“没有进展”的情况，否则 Agent 可能只是重复生成相似的方案。

重试次数只能限制损失，不能创造可靠性。真正的可靠性来自：每次重试都获得了新的信息，并且下一次行动和上一次失败有明确区别。

## 六、把“进展”设计成可以被记录的状态

Loop 如果只有一串对话历史，很快就会变得混乱。更好的方式是维护一个显式状态，例如：

```json
{
  "goal": "新增用户注册接口",
  "subgoals": [
    {"name": "路由已添加", "status": "done"},
    {"name": "参数校验已添加", "status": "done"},
    {"name": "重复用户名返回正确错误", "status": "failed"},
    {"name": "回归测试通过", "status": "pending"}
  ],
  "attempt": 4,
  "last_error": "duplicate username returns 500",
  "changed_files": ["api/user.py", "tests/test_user.py"]
}
```

显式状态有几个好处：

- Agent 不需要每一轮重新阅读全部历史；
- 评估器可以直接判断哪些子目标已完成；
- 失败以后可以从最近的稳定点恢复；
- 用户能够看懂 Agent 目前卡在哪里。

这和传统工作流引擎里的状态机有些相似，但 Agent Loop 通常允许模型在多个动作之间进行选择，所以它不是一条完全固定的流程。比较实用的设计是：**用状态机约束大方向，用模型决定局部动作。**

## 七、让 Agent 学会在局部失败后回到稳定点

复杂任务中，一个常见问题是：Agent 为了修复一个错误，修改了更多文件，最后整个项目比最开始更不稳定。

因此，Loop Engineering 需要关注检查点（checkpoint）。检查点不一定要很复杂，可以是：

- 每个子任务完成后的 Git commit；
- 一组测试通过后的工作区快照；
- 数据处理流程中间产物的版本号；
- 浏览器自动化任务中的页面状态记录。

有了检查点，循环就不再只有“向前走”这一种动作，还可以选择“回到最近一次已验证的状态”。

这点很重要，因为 Agent 的探索本质上带有试错性质。允许它回滚，意味着我们承认某些尝试可能失败，并且提前为失败准备了安全出口。

## 八、几个很常见的坏循环

### 没有评估器的循环

Agent 修改完代码以后，只要工具没有报错，就认为任务完成。这个系统实际上无法判断用户目标是否达成。

### 只会局部打补丁的循环

每次测试失败，Agent 都只修改报错所在的那一行，却从不重新审视数据结构、接口约定或整体方案。错误会在不同位置之间转移。

### 自我确认的循环

模型自己生成实现，自己阅读实现，然后自己得出“实现符合要求”的结论。生成者和评估者完全重合，容易形成虚假的确定性。

至少应该把部分判断交给独立的测试、规则或运行环境。模型可以参与评估，但不能成为唯一评估来源。

### 无限探索的循环

Agent 不断尝试新的工具和方案，看起来很积极，却没有明确的预算和停止标准。最后消耗了大量时间，仍然不能说明究竟哪里失败。

### 反馈过多的循环

把所有日志、所有历史动作和所有中间文件都塞回上下文，并不会让 Agent 更聪明。噪声会稀释真正重要的反馈，也会提高上下文成本。

循环需要的不是更多信息，而是**下一步决策所需要的最小充分信息**。

## 九、Loop Engineering 的一个实用设计模板

如果要给一个实际任务设计 Agent Loop，我通常会先回答下面几个问题：

1. 最终目标是什么？能不能写成明确的验收条件？
2. 任务可以拆成哪些相互独立、可以验证的子目标？
3. Agent 能执行哪些动作？哪些动作必须经过用户确认？
4. 每个动作完成后，环境会返回什么客观反馈？
5. 哪些失败可以自动修复，哪些失败应该触发重新规划？
6. 什么情况下算作没有进展？
7. 时间、成本、修改范围和风险上限分别是多少？
8. 如果中途失败，最近可以回到哪个稳定检查点？
9. 最终由谁确认完成：测试、规则、用户，还是多者组合？

这份清单看起来不像 Prompt，但它决定了 Agent 能不能从“会生成答案”变成“能完成任务”。

## 十、Loop 是 Harness 的动态部分

我现在越来越觉得，Harness Engineering 解决的是 Agent 的“静态能力”，而 Loop Engineering 解决的是 Agent 的“动态行为”。

工具注册、权限管理、上下文压缩、记忆存储，这些能力即使不执行复杂任务也可以单独存在；但只有当它们被放进一个反馈闭环里，Agent 才真正拥有持续完成任务的能力。

一个工具如果没有返回结构化结果，就很难成为有效反馈；一个记忆系统如果只保存历史、不记录哪些尝试有效，也很难帮助下一轮决策；一个权限系统如果没有在循环中定义哪些动作需要确认，也无法真正控制风险。

所以，Loop 不是在 Harness 之上额外加的一层装饰，而是把 Harness 的各个部件连接起来的运行方式。

如果说模型是负责提出下一步猜想的大脑，那么 Loop 就是让这个猜想接受现实检验的机制。模型可以犯错，循环不能没有反馈；模型可以探索，循环必须知道什么时候停止；模型可以生成很多方案，系统必须负责确认哪一个真的有效。

## 结语

Agent 的能力上限，可能由模型决定；但 Agent 能不能稳定地把任务做完，往往由循环决定。

一个好的 Loop 不会假设模型第一次就正确，也不会把所有失败都处理成重试。它会让每一次行动都产生可观察的结果，让每一次失败都能帮助下一次决策，并且在无法继续时及时停下来。

从这个角度看，构建 Agent 的过程有点像做实验：提出假设，执行实验，观察结果，修正假设，再决定是否继续。模型负责提出假设，环境负责提供现实，Loop Engineering 则负责把两者连接起来。

最终我们想要的，不是一个“回答得很像完成了任务”的 Agent，而是一个能够在反馈中逐步接近目标，并且知道自己何时真的完成、何时应该停下来的 Agent。
