这本书回答一个问题：把一个 Agent 从「能跑的 Demo」做成「可靠的产品」，中间差了什么。它的答案不是某个框架或某个模型，而是一套围绕模型构建的工程体系。

全书唯一的核心命题

Agent = LLM + 上下文 + 工具

= 大脑 + 眼睛 + 手脚

全书立场：方向认同，节奏务实

对于「模型变强后会不会吃掉 Harness」这个问题，书中的回答是：方向上不怀疑模型会持续内化 Harness（工具调用、长程规划都曾靠外部编排，如今已是原生能力）；但节奏上这个过程远比想象中慢——训练以月计，模型也无法一次内化真实业务中所有约束与偏好。

模型此刻的能力边界，就是 Harness 此刻的价值所在。模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。

核心公式与全书地图

书中给出两个公式。它们不是并列的两套骨架，而是同一事物在不同抽象层次上的描述：

生产形态下的完整展开
Agent   = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent  ↔ Environment            # Agent 与环境是交互的两方，不是彼此的组成部分

最小 Demo 只需 Model + 能构造上下文、暴露工具的 Harness；生产系统还要在同一边界内加入约束、验证和纠正。

一条最容易被误解的边界

Harness 不是「模型之外的一切」，而是 Agent 边界内、模型之外的运行与治理层。工具定义、调用适配器、沙箱的权限与重置机制属于 Harness；沙箱内随行动变化的文件和进程、外部数据库、网页、用户及物理世界属于 Environment。

物理部署位置不能决定概念归属——即使仿真环境与 Agent 运行在同一进程中，它仍然是 Environment。

全书最重要的杠杆

在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间——用本书的术语说，就是扩展上下文和工具。

许多看似需要「更聪明模型」的问题，其实只是接口问题：把任务所需数据纳入上下文，或把所需操作封装成工具，原本不可解的任务就可能变得可解。

两个产品例证：Manus 把 Deep Research、Coding、Computer Use 三条原本独立的路线合并进同一个生产级 Agent——取三类 Agent 观察空间与动作空间的并集；OpenClaw 又把接口延伸到用户的数字生活（多种消息渠道 + 本地 Gateway 连接云盘与本地文件系统）。

消融实验（1-1）最反直觉的两个发现

① 上下文组件并不等价。去掉工具定义或工具执行结果会直接夺走行动与闭环能力；去掉思考过程与历史消息的代价，则取决于其承载的信息能否从当前观测重建。

② 「给出了回答」不等于「完成了任务」。上下文残缺时典型的失败不是报错退出，而是一个看上去毫无破绽的答案——数据其实来自参数记忆，排版与真正基于观测的答案一模一样。

编排模式：从简单到复杂

WORKFLOW
工作流：确定性编排 执行路径由代码预先写死，LLM 只在节点内部工作。

优势：严格流程控制（「付款前不能预订」由代码强制）；安全性——攻击面被限制在单个节点内。
局限：缺乏变通，预设未覆盖的情况无法灵活应对。
AUTONOMOUS
自主 Agent：动态决策 执行路径由 Agent 根据环境反馈实时决定，本质上就是在循环中使用工具的 LLM。

优势：适合开放式问题，能识别失败并调整策略。
局限：成本更高、有复合错误风险，必须设计明确的停止条件。
Harness 很重要，不等于 Harness 越复杂越好

书中给了一个具体的反面例子：为「从百万条聊天记录提炼记忆」设计 Agent 时，AI 很容易迅速画出一条看似严谨的流水线（切分 → 提取 → 核验 → 身份解析 → 整理 → 合并复核 → 事实图 → 覆盖账本 → 不可变版本）。每个部件单看都有道理，组合起来却非常低效、不可靠——复杂工作流的执行拓扑是固定的，遇到新例外就继续加节点，架构越来越复杂、通用性越来越差，模型原本可以根据上下文处理的语义判断，反而被工作流写死了。

Manus 官网的概括是：“Less structure, more intelligence.” 好的结构不是替 Agent 预演全部思考，而是守住边界，并把边界内的决策空间还给模型。

Harness 里那些给模型能力短板打补丁的部分，会随着模型变强被模型自己内化。仅在第一章里这样的事就发生了好几轮：few-shot 示例与「一步一步思考」被指令微调和推理模型内化；输出格式修复、JSON 解析容错被结构化输出和原生工具调用内化；文生图的提示词改写被原生多模态能力吃掉。每一轮内化，消灭的都是「翻译」和「脚手架」这类适配层代码。

一句话立论

一个中等能力的模型配上精心组织的上下文，往往能胜过一个顶级模型在信息匮乏下的盲目摸索。

OpenAI 研究员翁家翌的概括更直接：「人和模型一样，最重要的是 Context。」他还指出「团队合作中最大的问题也是 context 的不一致」，而「AI 短时间内无法取代人的最大原因也是 context——因为 AI 跟人并不在同一个环境里面」。

这不只是技术问题，更是组织问题

大多数团队的关键知识都是隐性的：架构决策只有老员工记得，业务规则靠口口相传，重要背景锁在私聊记录里。如果团队本身就是一个信息黑洞，再好的 Agent 也无计可施。

因此有一个判断：对远程工作友好的团队往往也对 AI Agent 友好。Linux 内核就是范例——高度透明、文档驱动，信息是公开的、可检索的、结构化的。构建 AI 原生团队，首先是一场文档化运动，而不只是部署新工具。

KV Cache：三条必须记住的结论

本章以一个真实故障开场：某团队为了让 Agent「知道」当前时间，在系统提示词里加了一行时间戳。第二天首 token 延迟从 0.5 秒涨到 3–5 秒，月度推理账单几乎翻了一倍。

01
系统提示词和工具定义一旦确定就不要改。任何改动，哪怕多一个空格，都可能改变 token 序列，使首个不同 token 及其后的缓存无法复用；改动越靠前，影响越大。
02
动态信息永远追加到末尾——时间戳、用户状态等变化内容，作为新消息追加到对话末尾，而不是修改已有的系统提示词。
03
使用标准 API 格式，不要自行拼接消息。根本问题不在缓存，而在于偏离了模型训练时见过的格式，会削弱多步思考能力。
缓存不只是优化手段，而是架构约束

Claude Code 的实践揭示了一个深层模式：当 Prompt Cache 的经济效益足够显著时，缓存一致性会反过来主导系统的架构选择：

  • 提示词结构由缓存边界决定——每个运行时条件若放在缓存边界之前，就会把缓存键的变体数量翻一倍（N 个二值条件产生 2^N 种组合）
  • 子 Agent 必须与父 Agent 字节级对齐——提示词、工具定义、模型配置、消息前缀、思考配置逐字节匹配才能命中缓存
  • 工具结果的替换字符串在首次出现时就被冻结——即使会话重启也使用完全相同的替换串

缓存经济性不是事后优化，而是前置约束。

Agent 状态栏：把隐式状态变成显式知识

理论基础：上下文窗口是一台只有一半的检索引擎

它「检索」的这一半非常强——你问什么，注意力就能从成千上万个 token 里把相关记录捞出来。但它缺了另一半：没有「提炼层」。上下文里的东西从来不会被自动数一遍、建个索引或就地总结成一条结论。

任何「关于这些内容的结论」——一共多少条、有没有超标、进展到哪一步——模型每次要用都得从原始记录里现算一遍，而代价随上下文堆积量上涨。

典型场景：系统提示词要求「拨打每个商家不超过 3 次」，但打了 3 次之后 Agent 经常数不清，又打了第 4 次甚至陷入循环。解法是在工具结果中直接标明「本次是第 3 次呼叫该商家」。

状态更新的两种实现做法缓存代价
每轮替换移除上一轮状态，在末尾追加最新状态失效范围只覆盖上次注入后新增的消息，整个前缀仍可复用
持久追加状态消息永久留在轨迹中，每轮只追加新状态对缓存完全友好，但陈旧状态会累积占用 token

取舍公式（设状态 S token、两次更新间新增后缀 R token、更新 N 次、缓存单价为普通输入的 α 倍）：当 αSN/2 < (1−α)R 时倾向持久追加，否则倾向每轮替换。

状态栏的两条维护纪律

① 状态栏尽量用代码维护。实验发现模型几乎无条件地相信状态栏——你写「打了 3 次电话」，它就当真是 3 次，不会自己重算。这也意味着状态栏投毒风险值得认真对待。

② 谨慎删除原始上下文。状态栏是对原始上下文的一次有损投影，只提前算了「你预想会被问到」的维度。一旦有问题涉及未计算的维度，仅保留状态栏会导致准确率断崖式下降。

为什么「追加到末尾」不破坏缓存

这是 KV Cache 前缀性质的直接推论：因果注意力决定了每个 token 的键值对只依赖它之前的 token，因此在末尾追加新内容不会改变任何已缓存 token 的 K、V。所以这不是「预编译」，而是「只增不改」的追加式注入。

一个易误解点：「追加到末尾」只发生在工具/Skill 被发现的那一轮。此后这个 schema 块就固定在轨迹原位置，成为普通历史消息，而不是每轮被重新搬到最新末尾。

上下文压缩：三个动机与一个隐蔽故障

📏
长度与成本约束
最直观：窗口有限、token 越多越贵、延迟越高。
🧠
提升思考质量
更深也更易忽视：把需要思考才能得到的结论，变成可以直接检索的知识。
😰
缓解上下文焦虑
模型认为窗口即将耗尽时，可能在任务未完成前提前收尾。
上下文腐化（Context Rot）：装得下但找不到了

它与上下文溢出是不同问题：溢出是「装不下了」，腐化是「装得下但找不到了」——后者更隐蔽，因为 Agent 表面上还在正常工作，只是决策质量悄然下降。无关内容一旦占到上下文的大头，决策质量就会明显下滑。

隔离优于压缩

压缩是在信息已经进入上下文之后做减法；子 Agent 上下文隔离则更釜底抽薪——让大体积中间信息根本不进入主上下文。同一个「在代码库中找处理支付回调的函数」任务：主 Agent 亲自搜索可能把数万 token 原始代码纳入主上下文；委派给搜索子 Agent，主上下文只增加两条消息（任务描述 + 结论）。

压缩是有损的、需要额外 LLM 调用的事后补救；隔离则让噪声从一开始就与主上下文绝缘，主 Agent 的 KV Cache 前缀也完全不受影响。

Simple Notes（最小事实，O(1) 但丢失关联）→ Enhanced Notes（完整段落，语义完整但冗余）→ JSON Cards（三层嵌套，支持部分更新但结构刚性）→ Advanced JSON Cards（加入 backstory、person、relationship、时间戳）。

最后一种解决消歧问题：「张医生」可能是用户自己的牙科医生，也可能是父亲的心脏科医生——脱离情境就无法正确理解。

实践标准：关键且少量的数据用 Advanced JSON Cards 保证可检索性；大量且非关键的对话事实用 Simple Notes 降低成本；多数生产系统采用混合模式。

为什么原始文档不加处理放进知识库远远不够

CASE 1
黑猫白猫的计数问题 100 个独立案例（90 黑 10 白）。用户问「比例是多少」时受限于 top-k，大部分案例根本不会被检索到，模型只能基于不完整样本得出错误结论。

解法：预先生成摘要「共 100 只：90 黑（90%）、10 白（10%）」并索引。
CASE 2
优惠资格的边界问题 几百条工单各记录一个个案结论，没有任何一条写着资格范围本身。护士来问时有三重障碍：最近邻偏置（「医生」语义最近）、边界语义缺失（「仅限…，其他一律不适用」不存在于任何单条工单）、完整性信号缺失。

注意：第二重障碍调大 k 也解决不了。

结论：必须在索引阶段投入计算资源，对原始知识主动提炼、抽象和结构化——把「100 个个体案例」压缩为统计摘要，把「散落在几百条工单里的个案」提炼为带边界的明确规则。

知识更新：把知识库当成代码库

增量更新的核心做法

把每次知识变更当成一个 Pull Request。不只适用于可执行记忆；Markdown 知识库、用户记忆文件和规则文档同样应进入 Git，获得差异审查、版本历史、责任追溯和一键回滚能力。

生产环境不应让任何一个模型绕过审核，直接改主分支或线上向量库。

  • Proposer Agent 提交 PR：从原始证据发现新事实、冲突或过期内容，提出尽可能小而完整的 diff，同步维护链接、索引、时间元数据和证据引用
  • Reviewer Agent 独立审核：拿到变更前知识、diff 和原始证据，独立检查每个断言是否被证据支持；退回时须给出指向具体证据和行号的可执行意见
  • 双方迭代至收敛：设置最大迭代次数或成本预算，超限转人工，不能默认放行
  • 合入后再发布：CI 检查格式、链接、元数据、权限标签，通过后才从已合入版本增量重建索引
三条容易被忽略的要求

① Proposer 和 Reviewer 都必须是 Agent，而不是两次固定的 LLM API 调用——它们要主动搜索相关文档、追溯证据、运行检查，需要文件搜索、版本比较、测试执行等工具。

② 两者应优先使用能力相近但来自不同家族的模型（如 Proposer 用 Claude、Reviewer 用 GPT）。不同训练数据与推理习惯可降低在同一处犯同类错误的概率；能力则不宜悬殊。

③ 索引是可重建的派生物，Git 中已审核的知识才是真正的来源。

定期整理：增量更新的必要补充

增量更新及时，但每次只看到一个局部。长期运行后，多次局部正确的修改仍可能累积出全局问题。全量整理包含三项核心工作：去重去旧与合并、回到原始数据核查（不能只在已有摘要之间相互改写，否则早期遗漏会一代代传下去）、冲突解决与场景限定（不应简单「保留最新一条」，而要追溯各自信息源，检查是否分别在不同条件下成立）。

权限过滤必须下推到检索层

一旦敏感内容进入了 LLM 的上下文，就很难保证它不以某种形式泄露到最终回答里。多租户系统还需保证租户之间的向量索引和元数据相互隔离。

不是因为代码生成模型特别强，而是因为软件工程几十年积累的基础设施天然构成了一套强大的 Harness——测试套件提供验收标准，Linter 和类型检查器提供即时验证，Git 提供完美的版本控制和回退。

四条可迁移的 Harness 设计原则

01
约束优先于指导。能用代码强制的规则就不要用文档建议——前者是「做不了」，后者只是「建议别做」。
02
验证要自动化。人工审查是不可扩展的瓶颈。
03
反馈越快越好，越结构化越好。错误信息越详细、越接近发生时刻，纠正效率越高。
04
回退要可靠。Agent 在安全网内操作才能大胆试错。
约束的另一层目的：防止过程性错误

验收基线管结果对不对，执行边界管过程——即使结果正确，用错误方法达成也不行：修复数据库故障时直接把库删了重建（「修复」生效，但数据没了）；修复编译错误时把代码全删重写（编译通过，但实现没了）。

这类破坏性捷径总是存在：即使把限制写进最终评估指标，Agent 也常能找到绕过去的办法——这正是 reward hacking 在 Agent 任务中的日常形态。因此约束的是动作而非仅仅是结果。

故障与错误恢复：四层故障、分级恢复

层典型故障
API 层限流、服务过载、请求超时、连接中断、输出触顶被截断
工具层幻觉调用、参数畸形、执行抛异常，以及最危险的——工具反复返回同一错误而模型不加改变地反复重试
上下文层窗口溢出、压缩失败、轨迹结构损坏（工具调用缺少配对结果）

一个真实的死亡螺旋

Agent 因上下文溢出停止 → 触发「结束时自动提交代码」的停止钩子 → 钩子调用 LLM 生成 commit message → 再次上下文溢出 → 又一次触发钩子。

防护靠两条：在错误路径上禁用一切会再次调用模型的副作用逻辑；用递归深度计数器检测并打断残余连锁。

熔断阈值从哪来：生产数据而非拍脑袋

Claude Code 压缩熔断「连续 3 次」的阈值来自真实统计——曾有一个会话在这条恢复路径上连续失败三千余次，仅这类无效重试每天就在全球造成约 25 万次 API 调用的浪费；逾千个会话出现过 50 次以上连续失败。3 次正是「绝大多数故障已恢复」与「继续重试基本无望」之间的经验拐点。

错误处理的边界不是单次请求，而是整个恢复循环

在确认无法恢复之前，中间错误不应暴露给消费者——恢复期间扣留错误消息，恢复成功则消费者毫无感知，所有手段均失败后才统一呈现。

跨厂商接管：带得走文字，带不走凭证

模型的思考通常由可读文字 + 厂商附加的凭证构成。换一家模型仍读得懂文字，凭证换一家就失效；各家对凭证的要求还不一致，宽松的一端不做校验，严格的一端拒绝一切非自己签发的凭证。

设计原则：轨迹不该按任何一家的接口格式存储，而应保存为中立格式——思考拆成可移植文字与不可移植凭证，工具调用只记名称与参数，标识符在渲染时按目标厂商重新生成。中立轨迹的价值也不限于故障切换：第 7 章的评估重放、第 8 章的训练样本构造、第 9 章的经验提取，依赖的都是同一份产物。

Artifact 模式：让数据绕过 LLM

SQL 查询场景中，让 Agent 执行 SQL 后用自然语言描述结果效率极低——不仅消耗大量 token，更严重的是 LLM「抄写」数据时非常容易出错。

更好的方案：Agent 生成 SQL 作为独立可执行产物，系统直接查库并渲染表格。数据从数据库直达用户界面，完全绕过 LLM 这个「中间人」。

动态生成软件：把信任边界下移到数据层

当接口、工作流乃至数据访问代码都由 Agent 随时生成时，应用层不再稳定。安全目标不能是「保证 AI 每次都把权限检查写对」，而应该是：即使 AI 写错了代码，权限约束仍然无法被绕过。

做法：数据库行级安全策略、约束与校验器、受控视图或数据访问服务，加上由受信任运行时绑定、无法伪造的访问上下文。必要条件是所有数据访问路径都必须经过受信任的数据层。

Agent 为谁效忠：多方委托下的忠诚度

模型训练中形成了朴素默认——「谁在跟我说话，我就尽力帮谁」；但真实 Agent 常处在多方委托处境：替你砍价的 Agent，对面坐着的不是「需要被帮助的用户」，而是交涉对手。

实测显示一条忠诚度光谱，两端都会翻车：一端太老实（把底价直接抖给对手，被反复施压几轮就缴械）；另一端太多疑（连主人正当请求也拒绝）。这两种失败是一根跷跷板，很难两全。

提示注入本质上就是一次策反。因此 Harness 层要明确限定忠诚对象：主人指令优先级最高，一切来自外部交互方的内容默认降格为「可参考、但不具备指令效力」的数据。

回合制是模型与接口的一种交互约定，不是环境的性质。真实环境不会等模型作出反应：邮件在它思考时到达，用户在它说到一半时插话，页面在两次截图之间已经变了样，杯子在机械臂伸手的途中被碰倒。

事件处理的三种策略

CANCELLATION
取消式（紧急事件） 本质是为紧急事件提前制造一个安全点：停止当前操作 → 清空待处理队列 → 与紧急事件一起追加到轨迹 → 立即重新调用 LLM。

例：用户输入「停！我说错了」。
QUEUED
队列式（常规事件） 放入队列末尾不打断当前操作，等到达安全点再批量追加。

例：Agent 调用搜索后用户补充「只看最近一个月」，搜索结果返回时两个事件一起呈现，避免不必要的往返。

并行处理（独立轻量查询）：主任务分析大量数据时用户问「今天天气怎么样」。这类查询与主任务无关、需快速响应、成本低——用取消式会打断主任务，用队列式让用户等太久，应在并行推理会话中独立执行，并明确标记为「与主任务并行执行」以免 LLM 混淆。

紧急度判定：建议用轻量分类 LLM 做事件路由器

硬编码规则有局限——事件的语义决定了处理方式：「马上停下来」用取消式、「今天天气怎么样」用并行式、「报告需要用中文发给我」用队列式。

兼容同步接口时的占位符风险

核心思想：常态下让 LLM 看到标准同步轨迹，只在打断时插入占位符修复格式。但占位符带来语义风险——模型可能把「任务已启动」误当成「任务已完成」，在真实结果返回前作出依赖该结果的判断。应通过明确的任务状态和结果校验防止混淆。

工具接口设计层面的改进：把 phone_call 改成 initiate_phone_call——工具的名称和描述本身就要传达异步语义。

快慢分离不只是对延迟的妥协

它还是一种让交互能力与智能上限分别演进的模块化选择：前台快模型负责低延迟倾听与维持对话，后台慢模型负责推理与工具调用；更强的思考模型发布后只需替换后台，不必重训整套实时语音系统。统一路线则把推理与交互绑定在同一训练周期。

「端到端」的两个独立含义，别混为一谈

② 认知架构的端到端：实时交互与深度思考是否在同一模型内共享状态、共同训练。

两条轴彼此独立——一个系统完全可以在语音通路上端到端，同时在认知架构上保持快慢分离。

移动端：生态壁垒比技术更难

机器人：一个诊断实验

XLeRobot 案例的诊断价值

成本只有几百美元的机械臂，通过遥操作已经能完成连续多步桌面任务。这不只说明「硬件勉强可行」，更是一个明确的诊断证据：对于这个任务，硬件本体不是瓶颈，算法才是瓶颈。

诊断方法很直接：保持摄像头、机械臂、桌面布置和成功条件不变，先让人接管闭环。自主系统与人的差距，正体现在那些闭环能力上（靠近时减速、滑动时修正抓取点、失败后重新观察）。

大模型每秒通常只能推理 1—10 次，控制器却需要几十到上千次更新。动作分块把推理等待藏在执行时间里，但动作段越长，运动越平滑，模型在这段时间里看到的新画面却越少——伸手抓杯子时杯子被碰动，它可能仍在执行根据旧画面生成的动作。

VLA 的四个局限

训练数据有限（机器人演示远少于互联网文本）｜只学会模仿，不一定懂后果（行为克隆没有要求模型回答「这个动作会造成什么结果」）｜机器人各不相同｜观察可能过时。

所以：语言模型知道「杯子」是什么，并不代表它知道摩擦、接触、液体晃动会怎样改变未来状态。VLA 主要回答「现在应该做什么」，还需要世界模型帮助判断「做了之后可能发生什么」。

但也要划清界限：「会生成视频」不等于「能指导机器人动作」。世界模型必须知道动作是什么，并能预测动作对物体和环境的影响；预测只能帮助选择，不能代替验收。

一个关键认识

评估的对象不应只是模型，而应是模型与 Harness 的组合体。同一个模型在不同 Harness 中表现差异悬殊。完善的评估体系应能区分「模型能力不足」和「Harness 设计缺陷」这两类本质不同的问题。

区分手段——模型替换实验：固定 Harness 只换模型。换强模型分数不涨 → 瓶颈在 Harness；分数随模型能力大幅波动 → 瓶颈在模型。注意这与消融实验不同：消融是关闭 Harness 组件看整体变化（定位内部哪个部件重要），模型替换是固定 Harness 只换模型（区分瓶颈在哪）。

评估指标：两个容易混淆的口径

CAPABILITY CEILING
Pass@k · 技术奇观 k 次尝试至少一次通过即算通过。衡量能力上限——「这件事原则上做得到」。

适合科研发现、漏洞挖掘、开放式创作：人类可以从 k 条候选中挑出最好的那条。

Manus、OpenClaw 早期成功率不高、成本很高，但通用性带来较高 Pass@k，这些「技术奇观」在社交网络被大量分享，是产品成功的关键。
BUSINESS RELIABILITY
Pass^k · 业务可靠性 连续 k 次每一次都通过，且不触发一票否决项。

单次成功率 p=0.6、k=5 时：
Pass@5 ≈ 99.0%（看起来几乎总能成功）
Pass^5 ≈ 7.8%（连续五次不出错仍很难）

后者才接近支付、退款、权限变更、生产部署的要求。

两种必须防范的评判偏差

长度偏差：倾向给更长、更详尽的回复打高分，哪怕内容并不更正确——就像考试时对不会的题长篇大论期望「蒙对」。防范：Rubric 里显式惩罚冗长；配对比较时先把长度控制到相近；定期审计评分与长度的相关性。

位置偏差：系统性偏向出现在某个位置的候选。标准缓解是交换顺序各评一次取平均；更严格的做法是只有两次判决一致时才计入。

失败归因：定位首个错误

归因对象是首个导致任务偏离的错误

后续错误往往只是连锁反应，不能把最后一个报错简单当成根因。问题案例来自三类信号：用户明确纠正、用户点踩、事后通过状态检查/规则验证器/LLM 评审发现。

一个教科书级的归因案例（AndroidWorld T3A）

任务是把图库中 expenses.jpg 的开销录入记账应用。Agent 用 32 步完成全部操作，没有任何一步返回错误，最后自行宣告完成，验收却报告记录不存在。

逐步回看发现：第 8 步的思考里写着 "I cannot actually see the content of the expenses in the image"——它自己已经知道没拿到数据，却既没有停下也没有报告；到第 11 步，四条开销数据凭空出现。首个错误落在第 8 步，而那一步既没有报错，也不是一次工具调用。

根因归属极易搞错：T3A 是纯文本 Agent，观察空间里只有元素树、根本没有图像像素，所以根因不是「模型不会 OCR」，而是 Harness 的观察通道缺失。记成模型问题就会去换模型或做 OCR 训练；真正该做的是补观察通道。

「做对了但说错了」被整体成功率掩盖

τ²-bench 公开基线中，带信息告知要求的 704 次运行失败 240 次，其中 162 次信息告知出错；有 80 次（占全部失败的三分之一）环境状态正确，但信息告知错误。多数评估只检查环境状态，因此看不到这类失败。

看到表现下降时，应先检查评测系统本身，再动 Agent

常见误区是看到分数下降就立刻改 Agent 代码。评测系统本身可能先出了问题：环境资源不足导致进程被杀、验证器有 bug 把正确答案判为失败、测试用例与生产场景脱节。这些在结果数字上跟模型退化一模一样，只有审查完整轨迹才能区分。

统计显著性：别被噪声骗了

100 个用例、成功率 70% 时，95% 置信区间约为 70% ± 9 个百分点——「新模型 73% 对旧模型 70%」不足以支持切换。

同一批任务比较两个配置时应优先做配对分析（McNemar 检验或配对 bootstrap），而不是直接相减两个独立成功率。每个配置最好用 3–5 个随机种子，报告均值和波动范围。

全章两条主线

主线一：本章对照实验中，SFT 更容易记住示范，RL 表现出更好的泛化。但这是这些实验条件下测得的结果，不是普遍属性——数据足够多样、正则化得当时 SFT 也能泛化，奖励或环境有偏时 RL 也会过拟合。

主线二：数据和环境，比算法更重要。这是工业界最反直觉也最有价值的经验。掌握现成算法的基本用法即可，真正决定成败的是三件事：Mid-training 语料有没有补齐底座、示范数据有没有建立起行为协议、仿真环境与奖励能不能提供可靠反馈。很多场景下，只要前两类数据质量到位，你甚至根本不需要做 RL。

SFT 的本质：换了数据的「预测下一个词」

SFT 在数学上和预训练是同一个任务——都是预测下一个词、最小化同一个损失函数。差别只有两点：数据不同（人工准备的「输入—输出」对），以及损失只算在回答上（loss masking）。

这解释了 SFT 为何表现出记忆倾向：优化目标是让标注回答里每个 token 的概率尽可能高，也就是尽量复现示范。一句话概括：用极高的样本效率，把一套稳定的「输入→输出」映射与协议固化进参数。

RL 的两个硬前提

① 格式支持：如果模型吐出的 JSON 无法解析，奖励函数连「成功还是失败」都判断不了。

② 能力支持（更根本）：如果在合理的 k、温度和任务覆盖下实测 pass@k 仍接近 0，基础模型几乎生成不出成功轨迹。只给 0/1 奖励时，GRPO 的一组 rollout 很可能全为 0，组内优势直接消失；PPO 也看不到「应该往哪里移动」。把采样量继续放大只能以约 1/p 的速度等待偶然成功。

RL 擅长把已有但概率较低的成功行为推高，不擅长从全零奖励中凭空创造模型从未学过的知识和能力。

「必须先 SFT」只在特定条件下成立

实验 8-11 中 Llama-3.2-Vision-11B 在严格结构化输出设置下不经 SFT 直接 RL 会失败；但足够强、已有非零成功率的基模可以跳过 SFT——DeepSeek-R1-Zero 就是这种情形。它后来加入冷启动 SFT，主要是改善可读性与语言一致性，而不是为 RL 注入任务知识。

GRPO 一次训练迭代：四步

  • 让策略模型重复尝试：同一份初始代码复制到 16 个隔离沙箱，独立解决 16 次。每次包含完整的「阅读 → 修改 → 运行测试 → 提交」，这整条过程叫一次 rollout
  • 计算奖励：验证器在干净环境应用补丁并运行测试。假设 4 次通过、12 次失败，则前 4 条得 1、后 12 条得 0
  • 计算相对优势：组内平均成功率 4/16，通过的 4 条得正优势、失败的 12 条得负优势。若 16 条全败或全胜，相对优势会消失
  • 梯度下降更新策略：不是把某个成功补丁原样背下来，而是让「先复现问题、检查边界条件、修改实现并运行测试」更容易出现，「掩盖异常、改测试、没验证就提交」更少出现

粗略时间估算：复杂 Agent rollout 生成数十轮工具调用，最慢 rollout 约 2000 秒 + 梯度更新约 600 秒 ≈ 一个 step 43 分钟；训练 100 steps 接近 72 小时。

一个极易被当成浮点噪声的致命问题

大规模 LLM RL 常用 vLLM/SGLang 生成 rollout，再用 FSDP/Megatron 重算 log probability。即使加载同一份权重，浮点精度、归约顺序、张量并行方式、批大小的差异，也可能让同一 token 的 log probability 略有不同——于是更新前本应为 1 的概率比已经偏离 1：系统名义上同步了权重，数值上却把 on-policy 训练变成了 off-policy。

放大链条：log probability 小误差 → 指数化的概率比偏差 → 长前缀累积 → clipping/优势加权改变 → 梯度方向改变。若 4000 个 token 的 log ratio 都有同方向 10⁻³ 偏差，轨迹级比率会累积到 e⁴ ≈ 54.6。

工程对策：在任何参数更新之前，用同一批轨迹比较 sampler 与 trainer 的 token log probability——这是最直接的 on-policy 单元测试。

RL 环境：先问「我的仿真环境真的像真实世界吗」

这个问题比选 PPO 还是 GRPO 重要得多

环境一旦失真，策略就会失效。如果仿真里的客服总按固定套路回话、错误信息跟生产环境对不上，模型就会学到一套只在仿真里管用的「应试策略」。这是 RL 项目最常见的失败方式——不是算法不行，而是练习场与考场并不相同。

造不出环境怎么办：让模型扮演环境

第一层：合成工具返回值。ZeroSearch 用 LLM 扮演搜索引擎，并采用课程式设计——初期返回高质量文档，随训练推进逐步掺入噪声，促使学生学会从不完美结果中提取信息。全程没见过真实搜索引擎的模型，直接对接真实搜索时依然表现良好。

第二层：仿真整个环境动态。DreamGym 把环境动态蒸馏进推理式「经验模型」，批量合成 rollout。

但风险明确：模拟器的世界知识就是训练的天花板，模拟器的系统性偏差会被策略照单全收；更糟的是 RL 会主动寻找并利用模拟器的漏洞。稳妥做法是混合：模型模拟承担大部分交互量，辅以真实环境交互定期校准偏差。

奖励设计：三个维度 + 一个额外问题

维度选择原则
来自哪里可验证奖励（RLVR）｜人类偏好（RLHF）｜模型评判（GRM）规则越确定，奖励越便宜、可复现，也越不容易被钻空子
什么时候给结果奖励（ORM）｜过程奖励（PRM）密集反馈换收敛速度，稀疏反馈换探索空间
表达多少信息标量｜半标量｜向量｜生成式诊断每增加一个评价维度，就增加一种被钻空子的可能
reward hacking 与 reward seeking 的区别

reward hacking 是钻规则或实现漏洞拿高分；reward seeking 则是模型先在心里建立一个「评判器会看什么」的模型，再按猜测调整行为。后者不一定篡改测试或伪造结果，却可能在长程任务中自行设置一个过于简单的检查，刚好通过就提前结束。

所以「通过了 grader」不能自动等价于「任务完成了」：评判器是意图的代理，训练越强，模型越可能把代理当成目标本身。

RLVP：奖励结果，惩罚路径

结果奖励解决「事情有没有办成」，却表达不了「是否按规定办成」。真实环境通常是非对称验证器：检测「做了一个坏动作」便宜而可靠，证明「这一步确实取得了有意义的进展」却很难。

关键不是「奖励越密越好」，而是能否恢复组内差异：纯结果奖励在全败组和全胜组都会产生零方差；违规动作通常容易检测，惩罚几乎总能恢复差异；进展奖励只有在部分进展可达时才有效。

实证（实验 8-16）：TerminalBench 违规次数由 3.71 降至 0.66 而成功率基本持平；miniF2F 达到 0.9 成功率所需迭代从 7.0 降至 4.4。但软件修复中若所有 rollout 都无法通过任何测试，进展信号不可达，加入它不会带来收益。

没有更强的教师怎么办：OPSD 自蒸馏

同一个模型分饰教师和学生两角，但看到的上下文不同：教师版能看到「特权信息」（标准答案或已验证的正确解答），学生版只看到问题本身，却在自己采样的轨迹上向教师版的逐 token 分布对齐。

对着答案解释学生刚走过的路径，通常比独立探索更容易。但它不会凭空创造新知识——如果模型拿着答案也讲不清过程，自蒸馏就没有额外信号。

① 提炼材料决定归纳质量。仅给错误文本，得到的是泛泛的「教训」；补充工具职责清单后，才得到可执行的「职责归属」。

Loop 工程：把宣称变成证明

过早终止的三种形态，同一个根源

偷懒式假完成（测试没跑就报完成）｜过早放弃（一条路走不通就说办不成）｜假成功（以为办成了，实际闭环没走完）。

根源：在验证之前，「完成」只是模型的一句宣称，不是证明。

业界共识：循环的瓶颈在验证器，而不在模型。验证不可靠，循环转得再快，也只是把劣质产出更快地标记为完成。

可检查的系统不变量：模型可以提出「完成」，但不能批准自己的「完成」。

Agent 的故障天生是拜占庭式的

传统分布式系统大多只需防崩溃故障（部件停止工作）；Agent 却很少径直停止运行，而是继续给出看似可信的错误结论，且错误不会主动声明自己是错误。这正是拜占庭故障。交叉验证、多数表决都是拜占庭容错的经典手段。

三层护栏：按「被绕过的难度」排序

上下文层有一个结构性上限

处在同一个上下文里的 Agent，很难判断自己是否已经被注入。所以上下文层只能降低攻击成功率，给不出保证——这正是必须有下面两层的原因。

数据层的价值在于它不依赖上面两层是否正确：即使提示注入得手、生成的代码完全漏写了权限判断，越权操作仍会在数据层被拒绝。

护栏的另一类失败：误拒绝

为了降低危险请求被放行的概率，模型可能同时拒绝一部分合法但形式敏感的任务（经过授权的安全测试、模型蒸馏研究）。因此护栏评估不能只测「应当拒绝的请求是否被拦截」，还要测「明确允许的请求是否能够正常完成」。

反复出现的六个判断

01
「给出了回答」不等于「完成了任务」。上下文残缺、观察通道缺失、过早结束时，典型失败不是报错退出，而是一个看上去毫无破绽的答案。因此验证必须核实机器可独立复核的事实，而非 Agent 的自我陈述。（1 · 5 · 7 · 8 · 10）
02
约束优先于指导，能用代码强制的就不要用文档建议。Linter 规则、类型约束、CI 检查、数据层权限是「做不了」；系统提示词里的「请遵循…」只是「建议别做」。（1 · 5 · 9）
03
数据与环境比算法更重要。先验 > 环境 > 算法。Mid-training 语料决定底座、SFT 示范决定协议、环境与奖励决定 RL 能探索什么。造练习场往往比调模型更贵、更难。（7 · 8）
04
模型内化一层，Harness 就卸下一层。那些给模型能力短板打补丁的适配层代码会被逐轮吃掉——few-shot、CoT 提示技巧、JSON 容错、文生图提示词改写都已发生。但 Harness 转而兜底新的能力前沿。（1 · 5）
05
结构不是替 Agent 预演全部思考，而是守住边界。「Less structure, more intelligence.」复杂工作流的固定拓扑会把模型本可根据上下文处理的语义判断写死。（1 · 9）
06
一轮证据只支持与它规模相称的下一步。子集上的 4/4 不能写成系统整体 100%；73% vs 70% 不足以支持切换；两项优化的节省比例不能直接相加。（7）
